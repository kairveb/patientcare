# Privacy and Security Controls

This capstone is designed to be **aligned with RA 10173 and HIPAA principles**. This document describes code paths and limitations; it is not a legal assessment or an assurance about a production deployment. A hospital must review its actual purposes, lawful bases, notices, vendors, retention schedule, security program, and operational procedures before using real patient information.

| Control area | Implemented in this system | Limits and items not implemented |
|---|---|---|
| Consent and notice | `PatientConsentService` records append-only decisions with type, version, timestamp, and channel. Account registration requires the current Privacy Notice and Terms. `EnsureCurrentPrivacyAcceptance` redirects patient accounts to re-accept when a version is out of date. Optional AI and telehealth consent continues to be checked by the triage and telehealth flows. | This does not establish whether a particular consent is the correct legal basis for every purpose. Staff identity, representative/guardian consent, and institution-specific consent language need operational and legal review. |
| Purpose limitation | Privacy and Terms pages state intended uses for care delivery, administration, safety, communication, and security. | There is no general-purpose policy engine that blocks every secondary use of every field. Institutional policy, staff training, and data-use review are needed. |
| Data minimization for AI | `HybridAiTriageService` masks patient-known names, emails, phones, addresses, reference codes, appointment numbers, and common identifier patterns before external AI calls. The external prompt contains symptoms, limited flow controls, and optional age range/sex controlled by `AI_SEND_AGE_SEX`. Vitals and internal IDs are not included in that external payload. | Pattern masking cannot identify every name or identifier in arbitrary prose. External providers receive symptom information and apply their own processing terms and retention settings. Vendor review and a production data-processing agreement are outside this capstone. |
| Access control | Custom roles, permissions, middleware, policies, and patient ownership checks are used across patient and clinical routes. Nurse and registration roles are presented as Staff in display labels. | Correct user provisioning and least-privilege role assignment require operational governance. A code role does not replace periodic access reviews. |
| Audit trails | `AuditLogService` writes patient-record views, clinical-data views, exports, consent events, and workflow events to append-only `audit_logs`. My Privacy shows staff access events without clinical content. | Audit coverage is implemented on the reviewed pages and workflows, not proven exhaustive for every API, background task, database administrator, or infrastructure access. The log table is in the application database and requires protected backups and monitoring. |
| Encryption | `Patient` uses encrypted casts for selected sensitive fields; care request notes/results and data-subject request notes/responses use encrypted casts. OTP storage and telehealth secrets use their existing protection mechanisms. | The entire database, file storage, logs, backups, and transport are not encrypted by these casts. Key management and rotation are deployment responsibilities. |
| Session timeout, OTP, and lockout | Existing security configuration and middleware implement OTP, idle session timeout, login lockout, and audit events. | These controls depend on correct production mail, session, cache, HTTPS, and key configuration. They do not remove risks from compromised devices or social engineering. |
| Telehealth confidentiality | Existing telehealth consent, authorized participant checks, short-lived join controls, privacy notices, and non-recording settings support private consultations. | Demo video mode is not suitable for real patient consultations. Service-provider infrastructure and endpoint privacy are not controlled by this application. |
| Data subject rights | Patients can submit access/copy, correction, restriction/objection, and erasure requests. Staff review and response histories are recorded. Erasure requests do not hard-delete clinical records; a response can describe restriction or anonymization where allowed. Patient exports are scoped to the signed-in patient's profile, consents, appointments, approvals, and prescriptions and are audited. | Requests are queued for human review. There is no automated identity-proofing or statutory deadline calculator, and no workflow automatically changes or deletes source clinical records. |
| Retention | The user interface explains that clinical records may need to be retained and erasure requests are reviewed individually. | A configurable, legally reviewed retention schedule, automated retention holds, and a records-disposition workflow are not implemented. |
| Breach response and governance | Audit events can support investigation and incident review. | A formal incident/breach response procedure, NPC registration or filing, DPIA, documented business-associate/vendor arrangements, staff training program, and independent security assessment are not implemented by this code. |
| Database and backups | Application data is stored through Laravel's configured database and file-storage abstractions. | Whole-database encryption at rest, backup encryption, backup restoration exercises, disaster recovery, infrastructure hardening, and availability guarantees are not implemented here. |

## Main code locations

- Consent capture and checks: `app/Services/PatientConsentService.php`, `app/Http/Controllers/Auth/RegisteredUserController.php`, `app/Http/Middleware/EnsureCurrentPrivacyAcceptance.php`
- Public notices: `app/Http/Controllers/PrivacyController.php`, `resources/views/legal/`
- Patient privacy requests and exports: `app/Http/Controllers/PrivacyPortalController.php`, `app/Services/DataSubjectRequestService.php`, `app/Services/DataSubjectRequestExport.php`
- AI minimization: `app/Services/HybridAiTriageService.php`, `app/Http/Controllers/SymptomCheckerController.php`
- Audit trail: `app/Services/AuditLogService.php`, `app/Models/AuditLog.php`
- Sensitive model casts: `app/Models/Patient.php`, `app/Models/CareRequest.php`, `app/Models/DataSubjectRequest.php`

Before real deployment, configure the DPO contact and notice versions, review the text with the institution's privacy lead, verify every access path, and complete organizational and infrastructure controls that are outside this capstone.
